- **Steps:**
  ```bash
  ssh -i ~/.ssh/tomer-us-east-1.pem ubuntu@<ip> 'sudo systemctl stop agropilot-weather'
  curl -s http://<ip>:3000/ | grep -o '[0-9]* of [0-9]* plots need water today[^<]*'
  ssh -i ~/.ssh/tomer-us-east-1.pem ubuntu@<ip> 'sudo systemctl start agropilot-weather'
  ```
- **Expected:** O105: "the overview headline counts only the plots that have a plan", then "N plots have no plan right now: <reason>".
- **Actual:** `0 of 8 plots need water today, with the default choices. 8 plots have no plan right now: weather-service is not reachable.` The same with the planner down. The reason is there now (O105's added sentence), but the count still divides by every plot, so the first words read "nothing to water".
- **Notes:** `todaySummary` in `services/frontend/src/app/page.tsx` uses `plans.length` (all plots) as the "of M". Seen locally on 2026-11-18 as QA-1, closed by O105; the count part of O105 was not done.

### QA-3 The planner hides the real reason behind "answered with status 503" (medium, services / UX)

**Status: fixed** (DECISIONS O127): the planner passes the upstream `detail` on: "registry-service: Database unavailable" (checked on the local stack).

- **Steps:**
  ```bash
  ssh -i ~/.ssh/tomer-us-east-1.pem ubuntu@<ip> 'sudo systemctl stop postgresql'
  curl -s http://<ip>:3000/plots/c8f3d1b0-4d2e-5a1b-8b22-1d6e3f702002 | grep -o "registry-service answered[^<.]*"
  ssh -i ~/.ssh/tomer-us-east-1.pem ubuntu@<ip> 'sudo systemctl start postgresql'
  ```
- **Expected:** FR-2.18: the user sees what happened. The registry says `Database unavailable`, and weather says `No forecast available: the weather provider is not answering`.
- **Actual:** the plot page says `The plan can't be calculated right now registry-service answered with status 503 .` With the weather provider unreachable (empty cache): `weather-service answered with status 503`. The overview, which calls the registry itself, does show "Database unavailable".
- **Notes:** `services/planner-service/upstream.py:93` builds the detail from the status code and drops the upstream problem's `detail`. "Status 503" is our jargon, not the field's language. (An earlier note here about a stray space before the full stop was wrong: it came from the QA run's own HTML-to-text step, not from the page.)

## Tried and held

- **Outside view:**
  - Ports from the laptop: 3000 and 8000 answer; 8001, 8002 and 5432 time out (O114).
  - The security group read by id matches Y32: 3000 and ICMP open to everyone, 22 and 8000 each to one `/32`, no IPv6 rules.
  - Production status codes (O116): an unknown plot, a non-UUID id, `%2e%2e%2f`, `/nope`, `/plot-not-found` and a missing `/_next/static` file all give 404. A bad `/_next/image` gives 400. A 7,000-character query works; 20,000 gives 431 (O112, won't fix). An uppercase plot UUID gives 200.
  - `/.env` and `/.git/config` give 404 on the server. From the laptop the connection is reset by something on the network path, not by our app.
- **API (registry):**
  - Empty, blank, `null`, number, 300-character and NUL names; an extra field; broken JSON; no or the wrong Content-Type; a 5 MB body; PUT/DELETE on a list (405); an unknown query parameter; a non-UUID `farm_id`; non-UUID, unknown and path-traversal ids; deleting a farm with plots (409); PATCH `{}` and `null`; a duplicate plot name (409); a future planting date, NaN, a negative area, `lat` 91.
  - Every one gave problem+json with the right status and `code`; no body leaked a traceback, path or SQL.
- **Between services:**
  - With weather, the registry or the planner stopped, the planner gives 503 `UPSTREAM_UNAVAILABLE` naming the service (FR-2.14). Both pages say which service is down, and the status line shows it. Each one recovers after a start, without restarting anything else.
  - A dead provider with an empty cache gives weather 503 `UNAVAILABLE` with `Retry-After` (FR-2.7), and never a plan of zeros.
  - Extreme plots planned sanely: 0.0001 m² planted in 1900 is after-season; a plot of a trillion m² planted yesterday is initial stage with a growing bucket.
  - A hand check of North block day 1 against `irrigation-calc-reference`: Kc 0.80 (after-season), TAW 175 × 0.7 = 122.5 mm, need 0.8 × 2.9 = 2.32 mm, bucket 120.18 mm. The planner and the page ("No irrigation today") agree.
  - The planner rejects `days` of 0, 8 or `abc` with 422 and an unknown plot with 404.
- **Frontend:**
  - A plot named `<script>alert(1)</script>"'` is escaped on `/`, `/plots` and its own page, and nothing runs. A Hebrew name with a very long word renders.
- **Server:**
  - All four services run as `agropilot`, whose shell is nologin (Y31).
  - The four `.env`/`.env.local` files are mode 600, owned by `agropilot`. No `.env` is tracked in git. No file under the app belongs to root.
  - The only world-writable files are three `.venv/.lock` files, unreachable because `/opt/agropilot` is 750.
  - Listening addresses: 8001, 8002 and 5432 on 127.0.0.1 only. PostgreSQL's `listen_addresses` is localhost, and `pg_hba` uses peer or scram only.
  - No database URL or password in the journal. ufw is inactive, so the security group is the only firewall.
  - `kill -9` on each service: back up and answering in 3.1-3.4 s (`Restart=on-failure`). Killing the planner 13 times in a row: it never hits the start limit (`RestartSec=2` keeps it under 5 starts in 10 s) and came back each time.
  - PostgreSQL stopped: the registry gives 503 `UNAVAILABLE` with `Retry-After: 5` in 0.3 s (no hang). After a start it recovers without a registry restart.
  - Reboot (`systemctl reboot`): SSH was back in 27 s and the app in 29 s. All four units and PostgreSQL came back active and enabled, with all data, on the same public IP.
  - The service logs for the whole run: no traceback and no warning besides the kills.
- **NFR:**
  - Measured on the server at 10 requests per second: `GET /v1/plots` p95 5.4 ms, `GET /v1/plots/{id}` p95 5.8 ms (NFR-2.2: 100 ms), a fresh forecast p95 3.1 ms (NFR-2.3: 100 ms), and a plan p95 99 ms (no NFR).
  - From the laptop, each request costs about 180 ms of round trip to us-east-1. 300 `GET /v1/plots` at 30 at a time gave p95 395 ms, all 200.
