## Findings

### QA-1 Rounding makes extreme but valid plots show "0 L" next to 122.5 mm, and "0 mm" next to 2.4 billion litres (low, services / UI)

**Status: fixed** (DECISIONS O131): the registry bounds area to 1-1,000,000 m², rows to 0.1-10 m and emitters to 0.1-5 m, so neither plot can be created.

- **Steps:**
  ```bash
  F=$(curl -s -X POST http://<ip>:8000/v1/farms -H 'content-type: application/json' -d '{"name":"QA-tiny-huge"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["id"])')
  base='"crop_id":"tomato","planting_date":"2026-06-01","soil_id":"loam","emitter_id":"dripnet-pc-1.0","lat":31.25,"lon":34.79'
  curl -s -X POST http://<ip>:8000/v1/plots -H 'content-type: application/json' -d '{"farm_id":"'$F'","name":"tiny","area_m2":0.0001,"row_spacing_m":0.01,"emitter_spacing_m":0.01,'"$base"'}'
  curl -s -X POST http://<ip>:8000/v1/plots -H 'content-type: application/json' -d '{"farm_id":"'$F'","name":"huge","area_m2":1e12,"row_spacing_m":100,"emitter_spacing_m":100,'"$base"'}'
  # open http://<ip>:3000/plots/<id>?start_pct=0 for each
  ```
- **Expected:** the numbers on one card agree (`irrigation-calc-reference`: litres = irrigation mm x area). The `qa` skill counts an impossible number on screen as high even when the advice is right; here it needs absurd plots, so low.
- **Actual:** tiny plot (drip 10000 mm/h): planner `"irrigation_mm":122.5,"litres":0.0,"run_minutes":1`; the page says `Water for 1 min | 0 L on the plot (122.5 mm of water)` and `refill from 50 % to full 0 min`. Huge plot (drip 0.0001 mm/h): planner `"drip_mm_per_hour":0.0,"irrigation_mm":0.0,"capped":true,"litres":2400000000.0,"run_minutes":1440`; the page says `Water for 24 h | 2,400,000,000 L on the plot (0 mm of water)`.
- **Notes:** each number is rounded on its own (mm to 2 places, litres to whole litres), so one rounds to zero while the other does not. No real plot is 1 cm² or 10^12 m² with emitters 100 m apart; the registry accepts both (only `> 0`).

### QA-2 A normal stop of the frontend is logged as a failure (low, server)

**Status: fixed** (DECISIONS O132): `SuccessExitStatus=143` in the frontend unit; applied on the next `/deploy`.

- **Steps:**
  ```bash
  ssh -i ~/.ssh/tomer-us-east-1.pem ubuntu@<ip> 'sudo systemctl stop agropilot-frontend; systemctl is-active agropilot-frontend; journalctl -u agropilot-frontend -n 3 --no-pager; sudo systemctl start agropilot-frontend'
  ```
- **Expected:** a clean stop is not an error (the three Python units log "Deactivated successfully"); the qa-live skill treats any error in the service logs that QA did not cause on purpose as a finding.
- **Actual:** during the reboot at 12:42:59: `agropilot-frontend.service: Main process exited, code=exited, status=143/n/a` then `Failed with result 'exit-code'`. The unit is `failed` instead of `inactive` until it starts again.
- **Notes:** `next start` exits with 143 (128 + SIGTERM) when systemd stops it. `deploy/systemd/agropilot-frontend.service` has no `SuccessExitStatus=143`. No effect on the grower: the unit came back after the reboot, and `Restart=on-failure` does not fire on a stop. It does add a false "failed" to every deploy and reboot, which hides a real one in `journalctl -p warning`.
