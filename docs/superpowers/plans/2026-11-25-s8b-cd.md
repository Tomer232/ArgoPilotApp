## The flow

```
merge PR into main
  -> GitHub Actions "deploy" (runner)
       1. checkout the merged commit
       2. AWS: describe instance by id; start it if stopped; wait for running; read public IP
       3. AWS: open port 22 for the runner's IP /32 (description github-deploy-<run id>), keep the rule id
       4. wait for SSH (ssh-keyscan, retry)
       5. scp deploy/setup.sh + deploy/update.sh to /tmp/agropilot-deploy/
       6. ssh: pipe DB_PASSWORD into  sudo bash /tmp/agropilot-deploy/update.sh <github.sha>
            update.sh: read password from stdin -> setup.sh (idempotent) -> git reset to sha
                       -> write the 4 settings files -> deps -> build -> restart -> health checks
                       -> check the live commit equals sha
       7. always (also on failure or cancel): revoke the port 22 rule by its id
```

## Files

### 1. `.github/workflows/deploy.yaml` (new)

- `on: push: branches: [main]` and `workflow_dispatch` (a manual "Run workflow" button, for a deploy without a merge).
- `permissions: contents: read`.
- `concurrency: { group: deploy, cancel-in-progress: false }`: two merges never deploy at the same time (they would fight over the instance and the port 22 rule).
- One job `deploy`, `runs-on: ubuntu-latest`, `timeout-minutes: 20`.
- `env:` `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` from secrets, `AWS_DEFAULT_REGION: ${{ vars.AWS_REGION }}`. The AWS CLI is already on the runner; no extra action.
- Steps (each a short `run:` block with a `name:`):
  1. `actions/checkout@v7`.
  2. **Find the instance**: `aws ec2 describe-instances --instance-ids "$EC2_INSTANCE_ID"`, read the state. If `stopped`: `aws ec2 start-instances --instance-ids ...`. Then `aws ec2 wait instance-running --instance-ids ...`. Read `PublicIpAddress`, write it to `$GITHUB_ENV` as `EC2_HOST`. Any other end state: fail with a clear message.
  3. **Open SSH for this runner**: `RUNNER_IP=$(curl -s https://checkip.amazonaws.com)`; `aws ec2 authorize-security-group-ingress --group-id "$EC2_SG_ID" --ip-permissions "IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges=[{CidrIp=$RUNNER_IP/32,Description=github-deploy-$GITHUB_RUN_ID}]" --query 'SecurityGroupRules[0].SecurityGroupRuleId' --output text`; save the id to `$GITHUB_ENV` as `SSH_RULE_ID`.
  4. **SSH key and host key**: write `EC2_SSH_KEY` to `~/.ssh/deploy.pem` (mode 600); retry `ssh-keyscan -T 5 "$EC2_HOST"` up to ~2 minutes (a just-started instance needs time) into `~/.ssh/known_hosts`.
  5. **Deploy**: `scp` the two scripts to `/tmp/agropilot-deploy/`; then `printf '%s' "$DB_PASSWORD" | ssh ... "sudo bash /tmp/agropilot-deploy/update.sh $GITHUB_SHA"`. `DB_PASSWORD` comes from `secrets` through the step's `env:`, never on a command line, never echoed (GitHub also masks it).
  6. **Close SSH**: `if: always()` and only when `SSH_RULE_ID` is set: `aws ec2 revoke-security-group-ingress --group-id "$EC2_SG_ID" --security-group-rule-ids "$SSH_RULE_ID"`.
  7. **Summary**: the live link `http://$EC2_HOST:3000` and the commit, into `$GITHUB_STEP_SUMMARY`.
- The deploy never stops the instance (the owner stops it by hand; the course auto-stops it, O145).

### 2. `deploy/update.sh` (changed)

Usage: `printf '%s' "<db password>" | sudo bash update.sh <commit sha>`. Header comment says so.

1. Check: run as root, one argument that looks like a commit sha; read the password from stdin (`read -r`), fail with a one-line message if empty. Never print it.
2. Run `setup.sh` from the same folder as `update.sh` (`"$(dirname "$0")/setup.sh"`), with the password in its environment.
3. Code: as `agropilot`, `git fetch -q origin main`, then `git reset -q --hard <sha>`; print `git log --oneline -1`. A sha not on `main` fails here.
4. Settings, written from scratch every run (`install -m 600 -o agropilot -g agropilot`, never append):
   - `registry-service/.env`: `DATABASE_URL=postgresql+psycopg://registry:<password>@localhost:5432/registry?connect_timeout=3&options=-c%20statement_timeout%3D5000`. Written through a temp file with `umask 077`, no `echo` to the terminal.
   - weather and planner `.env`, frontend `.env.local`: copies of their `.env.example`.
5. Dependencies and build: as today (`uv sync --frozen --no-dev`, `npm ci && npm run build`).
6. Units: as today (`install` the unit files, `daemon-reload`, `enable` the four (new: needed on a fresh instance), `restart`).
7. Health: wait for each URL instead of a fixed `sleep 5` (retry up to ~60 s), same 4 URLs as today.
8. Check the live commit: `git rev-parse HEAD` equals the argument; print `Deployed <short sha>`.

### 3. `deploy/setup.sh` (new, idempotent)

The one-time setup from `deploy/README.md` steps 1-4 and 7-8, where every command first checks and does nothing if already done. Reads the password from the environment variable `DB_PASSWORD` (set by `update.sh`).

- Packages: `apt-get install -y` only if `postgresql`, `git`, `curl`, `xz-utils`, `sqlite3` is missing (`dpkg -s`).
- Node.js 22: only if `node` is missing or not v22. Same as README step 1 (nodejs.org tarball, checked with `SHASUMS256.txt`).
- uv: only if `uv` is missing (installer as in README step 1).
- Account `agropilot`: only if `id agropilot` fails.
- Code: only if `/opt/agropilot/app/.git` is missing, `git clone https://github.com/Tomer232/ArgoPilotApp.git`.
- Database: role `registry` created if missing; **its password set to `DB_PASSWORD` every run** (`ALTER ROLE`), so the GitHub secret is the one source of truth. Database `registry` created if missing. The SQL gets the password through `psql -v` and `:'pw'`, not inside the command line string.
- Seed: only if the `registry` database has no tables (`seed.py` itself also refuses). The live data survives.
- No unit work here; `update.sh` does it.

## Done when

1. Locally: `bash -n` on both scripts; the YAML loads with `python -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))"`.
2. On the instance, by the lead (owner approves), before the PR merges: copy the branch's two scripts to `/tmp`, run `update.sh <current origin/main sha>` with the password piped from the server's own `.env` (the fallback command): green; run it a second time: still green; live data still there (`Negev demo farm`).
3. After merge: the `deploy` run is green on its own, the live commit equals the merge commit, the security group has no `github-deploy-*` rule afterwards.
4. Rollback: re-run the run of an older commit (that has the new scripts), the live commit is the older one; then re-run the newest again.
5. Failure path: cancel one run during the build step; the "Close SSH" step still runs and the rule is gone.
6. Not tested here: a brand-new instance (needs the owner's OK to launch one in the shared account).

## Owner's choices (2026-11-25): all four recommendations accepted

1. **How the password reaches the server.** Recommended: piped on stdin into `update.sh` (never on a command line, never in a file in `/tmp`). Alternative: leave the registry `.env` alone and never write it from CI (simpler, but misses B10 "settings from secrets").
2. **Where the scripts come from.** Recommended: copied from the runner's checkout of the same commit, so a fresh instance (no clone yet) works and the scripts always match the deployed commit. Alternative: run the server's clone's `update.sh` (breaks on a fresh instance; old script runs the new deploy).
3. **Manual button.** Recommended: add `workflow_dispatch` (deploy without a merge, e.g. after the course stopped and restarted the instance). Alternative: merge-only.
4. **Fallback in the deploy skill.** Recommended: keep the on-server SSH command above as an emergency path only. Alternative: remove SSH from the skill entirely.
