## How we work on this plan

- One step at a time. The lead agent (Opus) gives a step to a cheaper builder agent (Sonnet), on its own branch from a fresh `main`.
- The builder does only that step, runs the step's "Done when" checks, commits, and reports. It does not push, open PRs or touch AWS or GitHub settings.
- The lead reviews the diff line by line, reruns the checks, and fixes or sends it back. Then the owner reviews. Only after the owner's OK: push, PR, merge.
- Repo rules apply to every step (`AGENTS.md`): small functions, a short docstring on every function, plain code, no extras. New decisions go to `DECISIONS.md` with the next number (after the open branches merge: Y39, O145, A73). Anything outside the course's requirements goes to `docs/extras.md`.
- Commit messages end with `Co-Authored-By: Claude <noreply@anthropic.com>`. No emojis anywhere.
- Never read `.env` files. Never print a secret.

### S6. 100% coverage (D5, B3)

Builder. Branch `coverage`. Three Python services and the frontend's `src/lib`.

Today: registry 96% (gaps in `config.py`, `db.py`, `errors.py`, `seed.py`), weather 97% (`config.py`, `errors.py`, `forecast.py`, `provider.py`), planner 99% (`config.py`, `errors.py`, `upstream.py`).

Python, per service:
- `uv add --dev pytest-cov`; in `pyproject.toml`: `[tool.coverage.run]` `branch = true`, `source = ["."]`, `omit = ["tests/*"]`; `[tool.coverage.report]` `show_missing = true`, `fail_under = 100`.
- The workflow runs `uv run pytest --cov --cov-report=term --cov-report=html` and uploads `htmlcov/` with `actions/upload-artifact@v7`, `if: always()`.
- For each missing line, a test that runs it **and asserts the result**. Use `monkeypatch` for what can't happen in a test (database down, provider failure, missing setting). The PostgreSQL-only branch in `db.py` gets a test that builds the engine from a `postgresql+psycopg://` URL without connecting.
- No `# pragma: no cover` without the owner's OK (list any you want in the report).

Frontend:
- `npm i -D @vitest/coverage-v8`; in `vitest.config.mts`: coverage `include: ["src/lib/**"]`, exclude the `*.test.ts` files, thresholds 100 for lines, branches, functions and statements; `npm test` stays as is, a new script `"coverage": "vitest run --coverage"`; the workflow runs `npm run coverage` instead of `npm test` and uploads `coverage/`.
- Unit tests for the untested files (`config.ts`, `health.ts`, `http.ts`, `planner.ts`, `registry.ts`, `utils.ts`, `use-now.ts`), with `fetch` mocked (`vi.stubGlobal`). Never call a real service.

Also: `.claude/skills/test/scripts/run-all.sh` runs `pytest --cov` and `npm run coverage`, so the deploy gate checks coverage too. Add `htmlcov/`, `.coverage`, `coverage/` to `.gitignore` if missing.

Done when: in each service `uv run pytest --cov` prints `TOTAL ... 100%` and passes; `npm run coverage` passes; `run-all.sh` is all PASS (stop the dev server first or accept the build SKIP and say so).

### S8. CD on merge to `main` (D6, D9, D10, B6-B12)

**Waiting for the IAM user the instructor creates for each student (2026-11-25).** This replaces the OIDC role first planned for D6: GitHub uses the IAM user's access key with the AWS CLI. Two parts, two branches.

**S8a. AWS and GitHub setup (lead + owner, no builder).** Touches only our resources:
- Check what the IAM user may do. The deploy needs: `ec2:DescribeInstances`, `ec2:StartInstances` on instance `i-02119bbbf95e78e0c`, `ec2:AuthorizeSecurityGroupIngress` and `ec2:RevokeSecurityGroupIngress` on our security group. Anything missing goes back to the instructor.
- GitHub Secrets: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (the IAM user's key), `EC2_SSH_KEY` (the `.pem`), `DB_PASSWORD`; all pasted by the owner. GitHub Variables: `EC2_INSTANCE_ID`, `EC2_SG_ID`, `AWS_REGION=us-east-1`.

**S8b. The pipeline (builder).** Branch `cd`.
- `.github/workflows/deploy.yaml`, `on: push` to `main`, `permissions: contents: read`, one job `deploy`:
  1. The AWS CLI with the IAM user's key from the secrets (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) and `AWS_REGION`.
  2. Find the instance by id; if stopped, start it and wait until running (as the `deploy` skill does). Read its public IP.
  3. Find the runner's IP; add a port 22 rule for that `/32` with a description `github-deploy-<run id>`.
  4. SSH as `ubuntu` with the key from the secret (`ssh-keyscan` the host first), and run `sudo bash /opt/agropilot/app/deploy/update.sh <github.sha>` with the `.env` values passed in.
  5. `if: always()`: remove the port 22 rule.
- `deploy/update.sh` changes:
  - Takes the commit as its argument: `git fetch origin main` then `git reset --hard <sha>` (a re-run of an old run is a rollback, B9).
  - Writes each service's `.env` from scratch on every run (never appends), from the values the workflow passes (B10, D10). The DB password never appears in the log.
  - Keeps the health checks at the end so a broken start turns the job red.
- `deploy/setup.sh` (new, idempotent, run by `update.sh` before the deploy): the one-time setup from `deploy/README.md` steps 1-4 (packages, Node, uv, the `agropilot` account, the clone, the PostgreSQL role and database, seed only if the database is empty). Every command must be safe on a fresh instance and on one deployed 20 times.
- `.claude/skills/deploy/SKILL.md`: becomes "merge the PR, watch the `deploy` run with `gh.exe run watch`, then check the live commit". The SSH path stays only as a fallback.
- `deploy/README.md`: the new flow, the secrets and variables, and how to roll back (re-run an old run).

Done when: a merge deploys by itself and the live commit equals the merge; a re-run of an older run puts the older commit live; the port 22 rule is gone after every run (also after a failed one); `update.sh` run twice in a row on the instance is still green. Not done in this step: a brand-new instance test (needs the owner's OK to launch one in the shared account).
